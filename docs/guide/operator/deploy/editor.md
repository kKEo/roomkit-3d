# The editor and publishing

This page explains the second page of the build, `edit.html`, and the publish flow it supports: an author edits a scene in the browser with a live preview, downloads the folder, and the folder is placed next to the viewer for everyone else. The code is `src/editor/`.

## What it is

`edit.html` mounts the same `<Viewer>` as `index.html` (`src/App.jsx`), with a pane on the left holding the scene. The pane shows it two ways, **Objects** (a tree and an inspector) and **Files** (the text), and both edit one `Map<path, text>`: the tree is read from the files and every tree operation is an edit of them, so the two never disagree and undo is a list of earlier Maps.

| Part | Code | Notes |
| --- | --- | --- |
| Files | `src/editor/bundle.js` | a `Map<path, text>` of `scene.json`, `poi/*.json` and `content/*.md`: the same shape `buildScene` reads through `readerFromMap`. `?scene=<name>` loads a published scene's text files into it; without it a one-POI template is used |
| Live preview | `src/editor/EditorApp.jsx` | 250 ms after the last keystroke the files go through `buildScene`, the same function the viewer uses. Success installs the scene with `setLoaded`, which keeps the visitor at the same POI; failure shows the `file › path: message` lines and marks the files in red, while the last good scene stays on screen |
| Scene tree | `src/editor/tree.js`, `Tree.jsx` | `sceneTree(files)` reads the room, the scenery (`decor`) and the stops (`poi`, in order) with their objects; nodes are keyed `room`, `scenery`, `stops`, `stop:<file>` and `<owner>:<index>` (owner `decor` or a POI file). The operations (`addToScenery`, `moveObject`, `makeStop`, `renameNewStop`, `dissolveStop`, `deleteStop`, `deleteObject`, `duplicateObject`, `moveStop`, `setObjectField`, …) are pure functions from files to files, tested in node. `errorsByKey` maps each `file › path: message` line of the build to the node it is about, for the ⚠ badges. Keyboard per the WAI-ARIA tree pattern; HTML drag and drop with a stated reason on a refused drop |
| Add, and the role of an object | `tree.js`, `AddMenu.jsx`, `bundle.js` (`objectTemplate`) | **+ Add** always appends to `decor`, with every prop of the prefab at its default, at `viewSpot(runtime.pose, room, taken)`: the floor point the camera looks at, inside the room, facing the camera, 2 m aside from occupied spots. Whether it is a stop is decided afterwards: `makeStop` moves the object into a new `poi/<id>.json` with `content/<id>.md` and lists it after the current stop (camera and marker left out, so they are auto-placed); the first rename of that stop renames its id and files too. `dissolveStop` moves a stop's objects to the scenery or another stop and drops the POI, its page (unless shared) and a `camera.start` naming it; `stopRefs` lists what else points at it (`goTo`/`zoom` actions, `#id` links) for the confirmation. Objects keep their world position and their own text layout when they move |
| Inspector | `Inspector.jsx`, `form.js` | an object's form is generated from its prefab's zod schema (`propFields`: numbers, booleans, strings, enums; nested values and unions as JSON); a prop that differs from the default is marked and can be removed (back to the default). Props that hold screens and every hotspot's action are left to `ScreenEditor.jsx`. A JSON tab edits the object's own text. A stop's label, kicker, camera (`runtime.pose`) and marker; the room's title, brand and size |
| Screens and clicks | `ScreenEditor.jsx`, `screenForm.js`, `fields.jsx` | props holding screens are found by schema identity (`screenKind`: `screenSchema`, `screenOrSource`, an array of `screenSchema`), so scene prefabs built on the SDK's schemas get it too. A screen's hotspot is asked from the prefab (`slotHotspot` probes `hotspots(props)` with a marker id): by `id` with a fallback (`scr0`…, `screen`), or the prop's name. A wall sketch (the prefab's `columns`), a source picker with only the keys `SOURCES[source].keys` lists, feed (url / stream / refresh / transform from `scene.json`), the click (`setClick`: `zoom: false`, or an action on the hotspot; a bare `{ "type": "zoom" }` in the scenery) and the id (`setScreenId` moves the action). List edits (`addScreen`, `removeScreen`, `moveScreen`) carry actions bound by place along. `edit.part` is the shown screen: a click on a screen in select mode sets it (`EditKeyContext` in `PlacedObject`, meshes in `editScreens`) and `EditMarks` outlines it. `PartActions` covers the other hotspots |
| Text edits | `src/editor/jsonEdit.js` | the tree and the form edit JSON through `parseTree` from `jsonc-parser`, splicing only the node they change: a replaced value keeps its old shape (one line or spread out), a new item or property follows its neighbours, and a moved object keeps its own layout, re-indented. A file that does not parse is refused with "fix it in Files first" |
| Preview link | `useStore › edit`, `src/prefabs/index.jsx`, `src/scene/EditMarks.jsx` | the editor sets `edit` in the store (null in the viewer): `mode` (`preview` / `select`), `selected`, `hovered`, `hidden`, `locked`, `frame(key)`. Every `PlacedObject` carries its tree key; hidden ones are not drawn; in select mode a click on a surface (not a line) selects it, a locked one lets the click through, and `useHotspot` and screens stop reacting. `EditMarks` draws a box (`Box3Helper`, over everything) around the selection and the hovered object |
| Handles in the room | `src/scene/Gizmo.jsx`, `configRotation` in `src/lib/math.js` | three.js `TransformControls` attached to the selected object's group (`editGroups`), in world space, `edit.tool` move or rotate (G / R), snapping 0.1 m and 15° unless Shift is held, Esc resets mid-drag. Listeners on the canvas, after the controls' own, stop a press on a handle from reaching R3F (no selection, no `onPointerMissed`) and `useInput` (no swipe). On release `edit.transform(key, { position?, rotation? })` writes the changed fields with `setObjectField`, one undo step; the rotation goes through `configRotation`, which picks the XYZ triple with the smaller tilts (`[0, 150, 0]`, not three.js's `[180, 30, 180]`). Loaded with `lazy()` from `Experience.jsx`, so only the editor fetches it |
| Import… | `src/editor/unzip.js`, `importZip` in `export.js` | a zip (stored or deflated entries, read with `DecompressionStream`, no dependency) holding a scene folder, a whole site (`scenes/index.json` names the scene) or a bare `scene.json`: the text files go into the Map, every other file under the folder is held in memory as bytes plus an object URL, and `resolveUrl` prefers those URLs over the published folder, so media and even prefab modules load from memory (`import()` of a `blob:` URL; its origin is the page's, so `guardOrigin` passes). Loose media files land under `media/` the same way |
| Export… | `src/editor/export.js`, `zip.js`, `tools/viewer-bundle.js` | two zips (stored, no compression): the **scene folder** (`<folder>/…`) or a **whole site** (the viewer's files, `scenes/index.json` naming this one scene, `scenes/<folder>/…`). Both hold the text files plus every file they refer to by a relative path (prefab and transform modules, media props, local feeds, fenced feed blocks) and every imported file, from memory first, else fetched from the published folder. The section also sets the scene's `camera.freeFly` and `camera.start` (a stop, or the pose of the preview's camera from `runtime.pose`), by rewriting `scene.json` |

A scene opened with `?scene=` resolves `media/…` against its published folder; a new scene's media paths resolve only once the files are imported or the folder is on a server. Files that cannot be found by reading the scene (assets a prefab module loads with `assetUrl()`, media a feed answers with) travel only when imported; otherwise they are added to the unzipped folder by hand. A module imported from memory resolves its own `assetUrl()` paths against a `blob:` URL, which fails: such a prefab needs its assets on a server.

The viewer's file list comes from `viewer.json`, which `tools/viewer-bundle.js` writes next to `index.html` at build time. In `vite dev` the same plugin serves `/__viewer/viewer.json` and `/__viewer/<file>` from a production build it makes on the first request (into `node_modules/.cache/roomkit/viewer`, redone when `src/`, `index.html`, `vite.config.js` or `package.json` is newer), so the export works from the dev server too; the first export takes a few seconds longer. A viewer built with `VITE_SCENES_BASE` reads scenes from that host and cannot be bundled with one: the editor says so and disables the button.

The viewer's fixed overlays move right by `--view-left` (set on `html.editing`), and they project through the canvas rectangle (`runtime.view`), which is why the room, labels and zoomed screens stay aligned beside the pane.

## Publishing a scene

1. In the editor, set the **folder** name (letters, digits, `-`, `_`), open **Export…** and click **Scene folder .zip**.
2. Unzip it. Add any file the editor listed in red (it could neither find it in memory nor fetch it) into the folder.
3. Put the folder in `scenes/` next to the deployed `index.html` (or in `public/scenes/` in the repository, so it ships with the next build and is covered by `make test`).
4. List it in `scenes/index.json` (the `scenes` array; `default` names the scene the bare URL opens).
5. Share `…/?scene=<folder>`. Deep links to a POI are `…/?scene=<folder>#<poi-id>`.

The published viewer is view-only by construction: it is the same `index.html` as before, and it reads the folder as data. No build is needed for new or changed scenes (see [Build and deploy](deploy.md)). To keep the editor off the public site, do not deploy `dist/edit.html` and `dist/assets/edit-*.js`.

## Exporting a site

The other route, for a scene that gets a host of its own: **Export…**, set *Allow free flight* and *opens at* (a stop, the whole room, or **Use current view** for the pose the preview's camera has now), then **Whole site .zip**. Unzip `<folder>-site.zip` onto any static host that follows the [hosting rules](deploy.md#hosting-rules); its `index.html` opens that scene. Links to other scenes (`openUrl` actions with `?scene=…`) have no target in such a site, and the fonts still come from Google unless the scene sets `theme.fontsUrl` to `""`.

## Limits of this first editor

- One object at a time: no multiple selection, no handles for a whole stop, and no scale handle (scale is in the inspector). The handles move along the room's axes, not the object's own. Hidden and locked marks are not saved, and they follow objects through the tree's own moves but not through edits typed in Files.
- The form covers each prop's top level; nested settings (a screen config, a list of screens) and `actions` are edited as JSON. Content blocks (`content.blocks`) have no form yet; `src/ui/blocks/schema.js` carries what one would need.
- Media are imported into memory, not uploaded anywhere: they travel in the exported zip. The browser holds them, so a very large video makes the page heavy; the zip is built in memory too (no ZIP64, so under 4 GB).
- No server: the export is the hand-off. A hosted flow would `PUT` the same files to a bucket and append to `index.json`.
